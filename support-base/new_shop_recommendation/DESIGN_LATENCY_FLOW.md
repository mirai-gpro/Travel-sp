### 構造上の制約（現行フロー）
- 初回カードは「推薦 LLM の全件完了 → 検索 → 選択 LLM」の後になる。そのため最短でも 9.6 + 1.3 + 5.3 ≒ 16 秒かかる。
- **初回カードを 5 秒以内にするには、次の 2 つが両方とも必要。** どちらか一方では目標に届かない。
  1. 推薦の 7 件すべてが終わるのを待たずに、1 件目の処理を始める
  2. 5 秒かかる LLM 同一性判定をクリティカルパスから外す

## 2. 全体フロー案

### フロー P（推奨案）: ストリーミング推薦 × 店舗単位パイプライン × 名称解決

現行の推薦方針（LLM の知識で推薦し、Maps で存在確認する）、プロンプト、モデルは維持する。

```
t0  Live が search_shops を発火（function call）
 │
 ├─ 推薦 LLM（stream=true、プロンプト・7件・LOW は変更なし）
 │     店舗 k の name / area_hint が確定した時点で ──┐（k = 1..7、順位順に流れてくる）
 │                                                  ▼
 │   [店舗 k の処理。店舗ごとに並列で走る]
 │     1. resolveNames（店名 + 地区）          ← B5。LLM 不要
 │        ├ HIGH      → Place Details（国コード・営業状態）→ 確定
 │        └ MEDIUM / NOT_FOUND
 │              → Agent Tools searchText + 選択 LLM（D と同じ判定。この店舗だけ）
 │                → 締め切りまでに判定できなければ不採用（別店舗で穴埋めしない）
 │
 ├─ カード送信: 確定した店舗を推薦順位どおりに並べ、累積リストで shop_search_result を送る
 │     （1 件目 → 1〜2 件目 → …。いまのフロントは受け取るたびに全カードを描画し直す）
 │
 └─ 確定 5 件に達した時点、または締め切り（10 秒）で:
       Live の tool_response を 1 回だけ送る（narration は確定した店舗のみ。中身は現行どおり推薦 LLM 由来）
```

**初回カードの時刻の式**: `T(推薦の 1 件目が確定) + T(resolveNames) + T(Details ≒ 0.1 秒)`

- 初回 5 秒を満たす条件: 推薦の 1 件目が約 3.5〜4 秒以内に確定し、かつ resolveNames が約 1 秒以内で終わること。**どちらも M1・M2 で計測するまで不明。**
- 全 5 件 10 秒を満たす条件: 推薦の 5 件目が約 8 秒以内に確定すること。MEDIUM / NOT_FOUND の店舗は選択 LLM（約 5 秒）を待つと 10 秒を超えるため、締め切りで打ち切る。

**品質の扱い**
- HIGH 判定の精度が D と同等以上かどうかで、このフローの成否が決まる（M2）。
- MEDIUM / NOT_FOUND の店舗は、D と同じ選択 LLM で判定するので品質は D と同等になる。ただし時間内に判定できない店舗は表示されない。
- 実在しない推薦（ハルシネーション）は NOT_FOUND になって除外される見込み。その分、5 件に届かない検索が出る。

### フロー Q（比較案）: グラウンデッド先行（B7）

```
t0 → Agent Tools searchText（ユーザーの依頼文、pageSize 5 または 10[Pro]）≒1.3 秒
   → 候補ごとに Place Details（並列）≒0.1 秒
   → LLM が実在候補の中から順位付け（出力は候補 ID と短い理由だけ）
   → カード送信 → tool_response
```

- 実在しない店舗の推薦（すり替え以前の問題）は構造上なくなる。同一性判定も不要になる。
- 推薦の出どころが変わるため、「33秒版以上の推薦品質」を満たすかどうかは未評価（M3）。
- 確定方針の変更になるので、採用するには承認が必要。
- 読み上げも Grounded Output になるため、音声インターフェースの開示要件（Agent Tools の attribution ガイドライン）への対応が必要になる。

### フロー R（参考）: E 方式 + ストリーミング
- 最も速い見込みだが、すり替えは E と同等（30 試行で 19 件）。推奨しない。

## 3. Live・ショップカード・UIKA との連携（コードで確認した事実と必要な変更）

**現行のコード（`live_api_handler.py` の `_handle_shop_search` → `send_tool_response`）**
- `shop_search_result` を 1 回 emit した後、tool_response を 1 回送っている。
- 読み上げデータ（narration）は推薦 LLM 由来の項目だけで、Maps のコンテンツは含まない。

**フロントの現行動作（`core-controller.ts`、`ShopCardList.astro`）**
- `shop_search_result` を受け取るたびに、待機オーバーレイを消して `displayShops` を呼ぶ。
- `displayShops` はコンテナを空にしてから全カードを描き直す。
- したがって、バックエンドが累積リストを複数回送れば、**フロントを変えなくても段階表示になる**。
- ただし受信のたびに次のことが起きる。体感上の問題がないかは実機で確認が必要。
  - 全カードの再描画（画像の再読み込みでちらつく可能性）
  - スマホでのスクロール
  - `response` の追加（現状は空文字）
- Agent Tools の結果を使う場合、カードに attribution（タイトルと URL）と placeUrl を表示する必要がある（規約 §10.2.1）。**フロント側の変更が必要。**

**Live（Gemini 3.8 Live）**
- tool_response は「確定 5 件、または締め切り時点」で 1 回だけ送る（現行どおり）。
- 途中で tool_response を分割して送れるかどうかは、Live の仕様を確認していない（知識ベース外）。この設計では分割を前提にしない。
- そのため、**カードは先に出るが、読み上げは確定後（10 秒以内）に始まる**。

**UIKA FULL133 / LAM / A2E / 二重リセット / Greeting**
- 変更しない。この設計で変えるのはショップ検索のバックエンド処理だけ。

## 4. 次のゲートで行う計測（製品コードは変更しない）

| ID | 計測内容 | 方法 | 判定基準（案） |
|---|---|---|---|
| **M1** | ストリーミング推薦の到達時刻（1 件目〜7 件目が確定する時刻、TTFT） | 同じプロンプト・モデル・LOW で stream=true。通常 10 クエリ × 3 回 | 1 件目の p50 ≤ 4 秒、5 件目の p95 ≤ 8 秒 |
| **M2** | resolveNames の精度とレイテンシ | 既存の照合済み 132 件（推薦名 + 地区）を入力し、返った place を Details の名称・住所で照合 | HIGH の誤り（別店舗）が D の誤り率 3.7% 以下。p95 ≤ 1 秒 |
| M3 | グラウンデッド先行（Q）の品質（任意） | 同じ 10 クエリで、候補の質を 33秒版の推薦と比べる | ユーザー評価 |

M1 と M2 は既存の資産（推薦プロンプト、照合済み 132 件）を使えるため、少ない API 呼び出しで判断できる。

## 5. リスクと未確認事項
1. **M1**: thinking の時間が出力の前にまとまって発生する場合、ストリーミングにしても 1 件目は早く届かない。その場合、初回 5 秒は B2 または B3（どちらも方針変更）か、フロー Q でしか実現できない。
2. **M2**: resolveNames が日本語の店名や表記揺れ、支店を区別できない場合、HIGH の精度が足りず、フロー P は品質目標を満たせない。
3. **推薦 LLM のハルシネーション**: 実在しない店舗の推薦は、どのフローでも件数不足の原因になる（フロー Q を除く）。
4. **締め切りによる打ち切り**: 10 秒で打ち切ると、D なら判定できた店舗が表示されないケースが出る。
5. **段階表示の UX**: 再描画のちらつき、読み上げ開始の遅れなど、実機での確認が必要。
6. **規約**: Agent Tools を使う経路では、カードの attribution 表示が必須（フロント改修）。resolveNames は place ID だけを返すが、表示に関する要件は公式ページで再確認する。
