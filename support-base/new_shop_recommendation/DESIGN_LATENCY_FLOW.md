## 3. 軽量な店舗同一性判定（仕様）

参照実装: `poc/light_identity.py`（評価専用。エンジンには組み込んでいない）。LLM も外部 API も使わない。

### 3.1 入力
- **推薦側**: 推薦店名、推薦エリア、検索エリアの都道府県と中心座標。中心座標は、ユーザーの依頼文から既存の Geocoding で求める。
- **候補側**: Agent Tools searchText が返した place ID で取得した Place Details の次の項目。
  - `name`
  - `formatted_address`
  - `types`
  - `business_status`
  - `geometry.location`

### 3.2 判定順序と 3 分類

| 順 | チェック | 結果 |
|---|---|---|
| 1 | 営業状態が `OPERATIONAL` 以外 | **DIFFERENT**（closed） |
| 2 | `types` に飲食業態（restaurant, cafe, bar, food, meal_takeaway, meal_delivery, bakery）を含まない、または駅・建物・商業施設・地名（train_station, transit_station, shopping_mall, department_store, premise, route, locality, sublocality, political, lodging など）を含み restaurant を含まない | **DIFFERENT**（not_a_store）。駅・建物・商業施設を店舗として採用しないための判定 |
| 3 | 住所に検索エリアの都道府県が含まれない | **DIFFERENT**（prefecture_mismatch） |
| 4 | 検索エリア中心から 3 km を超える（オフライン評価では座標がないため市区で代替） | **DIFFERENT**（area_mismatch） |
| 5 | 正規化した中核名が一致する | **SAME**（ただし支店表記が食い違えば AMBIGUOUS、候補が別館・本館なら AMBIGUOUS） |
| 6 | 英字表記とかな・漢字表記で、機械的に比較できない | **AMBIGUOUS**（script_differs） |
| 7 | 中核名が 1 文字（響・雷・凡など） | **AMBIGUOUS**（short_core）。名前だけで別店舗と断定しない |
| 8 | 中核名に共通する 2 文字の並びがない | **DIFFERENT**（name_unrelated） |
| 9 | それ以外（部分一致、屋号の追加など） | **AMBIGUOUS**（name_partial） |

### 3.3 表記揺れ・正式名称・支店名の扱い
- **正規化**: NFKC 正規化、小文字化、カタカナをひらがなに変換、記号・空白・長音を除去する。
- **除去する一般語**: 業態・料理の一般語（焼鳥、天ぷら、割烹、カフェ、串かつ、ジンギスカンなど）と地名（銀座、祇園／ぎをん、梅田など）を除いたものを「中核名」とする。
  - 除いた結果が 2 文字未満になった場合は、地名を残したもの、さらに元の名前の順に戻して使う（例：「さっぽろジンギスカン」）。
- **括弧内の扱い**: 括弧内の名前（例：「そらのいろNIPPON」「（夜空のジンギスカン 本店）」）も比較対象に加える。
- **支店表記**: 末尾の「総本店・本店・別館・本館」と、2 語目以降の「〇〇店」や地名を含む語を支店表記として分離する。
  - 本店と総本店は同じ扱いにする。
  - それ以外の支店名が食い違う場合は AMBIGUOUS にする。
- **別館・本館**: 推薦店と別の店舗である可能性があるため、AMBIGUOUS にする。

### 3.4 採用規則
- **SAME**: 即採用する。
- **AMBIGUOUS**: 無条件には採用しない。時間に余裕がある場合だけ、その店舗についてグラウンディング選択 LLM（方式 D と同じ判定）で確認する。締め切りまでに確認できなければ不採用。
- **DIFFERENT**: 採用しない。同じ店舗の検索結果に別の候補（2〜5 位）があれば、それに対しても判定を続ける。
- 採用された店舗が 5 件に満たなくても、別の店舗で穴埋めはしない。

### 3.5 規約に沿ったデータ利用と出典表示
- **Agent Tools の summary**: 選択 LLM のグラウンディングにだけ使う（Service Specific Terms §10.2.1）。軽量判定には使わず、summary から店名を抜き出すこともしない（§10.3.1）。
- **place ID と Place Details**: 公式に許可されている「place ID を他の Google Maps Platform API で利用する」使い方で Details を取得し、その結果を判定とカードに使う。
- **カード**: Agent Tools の `attribution`（title / url）と `googleMapsLinks.placeUrl` を保持する。表示にはフロントの改修が必要（§5.4）。
- **保存しないもの**: summary と Place Details の内容。

### 4.1 品質（推薦店単位。推薦店 118、そのうち正しい実店舗がわかっている 81）

| 方式 D（全件を選択 LLM） | 77 | 4 | 7 | 4 |
| 方式 E（1 位を即採用） | 74 | 17 | 10 | 7 |

**ペア単位の内訳（132 件）**

| 判定 | O（同一） | X（別店舗） | ?（判定不能） |
|---|---:|---:|---:|
| SAME | 68 | 0 | 5 |
| AMBIGUOUS | 13 | 13 | 8 |
| DIFFERENT | 0 | 24 | 1 |

**SAME と判定された「判定不能」の 4 店舗**（正解とは扱っていない）
- 銀座 吉兆（天ぷらカウンター）→ 銀座 吉兆
- 中目黒 鳥よし 本店 → 鳥よし
- 祇園 まつもと → 鮨まつもと
- 炭火焼鳥 カメヤ → かめや

**限界**
- 規則は同じ 132 件を見ながら調整した（同一データで調整と評価をしている）。未知のデータでの精度ではない。
- 候補は 1 位だけで、2〜5 位の候補、`types`、座標はログにないため評価していない。
- 以上は統合 PoC（§6）で検証する。

### 4.2 速度（モンテカルロ 20,000 回）

**方法**: 中央値を単純に足すのではなく、次を試行ごとに組み合わせて時刻を算出した。
- M1 の店舗別確定時刻 30 試行
- D1.7E の Agent Tools・Details・選択 LLM の実測値 30 試行
- D1.7E の試行ごとの推薦店構成と、各店の判定結果

**モデルの扱い**
- 推薦順位はログから復元できないため、無作為に並べた。
- Agent Tools と Details は、7 並列バッチの実測値を 1 店舗あたりの値として使った（保守的）。
- 選択 LLM は 7 店舗まとめての実測値を 1 店舗あたりに使った。1 店舗だけの時間は未計測。

| 方式 | 初回カード p50 / p95 | 初回 5 秒以内 | 10 秒で 5 件 | **10 秒で正しい 5 件** | 5 件中の別店舗（平均） |
|---|---:|---:|---:|---:|---:|
| 軽量判定のみ | 4.5 / 8.5 秒 | 63% | 16% | 9% | 0.00 |
| 軽量判定 + 曖昧は選択 LLM（実測値） | 4.5 / 8.7 秒 | 63% | 18% | 11% | 0.01 |
| 同（選択 LLM を 1 店舗 2.5 秒と仮定） | 4.5 / 8.0 秒 | 63% | 26% | 16% | 0.02 |
| 方式 D をパイプライン化（実測値） | 9.5 / 12.6 秒 | 0% | 0% | 0% | 0.03 |
| 方式 E をパイプライン化 | 4.2 / 6.4 秒 | 82% | 60% | 20% | 0.56 |

**制約がどこにあるかの切り分け**（同じモデルで条件を変えた結果）

| 条件 | 10 秒で正しい 5 件 |
|---|---:|
| 時間制限なし：軽量判定 + 曖昧は選択 LLM | 48%（実測の方式 D 14/30 = 47% と一致。モデルの妥当性を確認） |
| 照合・Details・LLM の時間をすべて 0 とした理論上限 | **47%** |
| Agent Tools 0.8 秒・選択 LLM 1.5 秒と仮定 | 32% |

### 4.3 評価から導かれる結論
1. **品質**: 軽量判定 + 曖昧なものだけ選択 LLM にかける方式は、方式 D より誤採用が少なく、回収も多い（79 / 1 / 2 対 77 / 4 / 4）。同一性判定の方式としては第一候補になる。
2. **時間**: 照合を 0 秒にしても、10 秒で正しい 5 件は約 47% が上限。原因は推薦 LLM 側にある。
   - 推薦 7 店舗のうち実在を確認できるのは平均 5〜6 店舗しかない。
   - 6・7 店舗目の推薦が確定するのが p50 で 7.7〜8.7 秒と遅い。
   - **照合を速くするだけでは、正しい 5 店舗を 10 秒で出すことはできない。**
3. **初回 5 秒**: 軽量判定だけでも約 63%。上位の推薦店が実在しない・曖昧な場合に初回カードが遅れる。

## 5. 全体フロー v0.2（推奨案：フロー S「店名先行ストリーミング × 店舗単位照合」）

§4.3 の 2 の制約は、照合を変えるだけでは解決しない。推薦段階で「照合に回す店名」を早く・多く揃える必要がある。そこで推薦を次の 2 段に分ける。**この分割は推薦プロンプトとスキーマの変更にあたるため、承認が必要**（§7）。

```
t0  Live が search_shops を発火
 │
 ├─[推薦A] 店名リスト LLM（stream=true、gemini-3.8-flash LOW、tools なし）
 │     出力は rank・name・area_hint だけ（理由・特徴は出さない）。推薦の観点・順位付けの指示は現行プロンプトと同じ
 │     店舗が 1 件確定するたびに ──┐
 │                                 ▼
 │   [店舗ごとの照合。並列]
 │     1. Agent Tools searchText（1 店舗、ja / JP / pageSize 5）
 │     2. 上位候補の Place Details（並列）
 │     3. 軽量同一性判定（§3）
 │        SAME      → 確定（カード候補）
 │        AMBIGUOUS → その店舗だけグラウンディング選択 LLM（締め切りまでに終わらなければ不採用）
 │        DIFFERENT → 次の候補。全候補が DIFFERENT なら不採用（穴埋めしない）
 │
 ├─[推薦B] 説明生成 LLM（推薦A の店名リストが揃った時点で開始。並列）
 │     確定した店舗について specialty・reason を生成する（カードの説明文と Live の読み上げ用）。Maps の情報は渡さない
 │
 ├─ カード: 確定した店舗を推薦順位どおりに並べ、累積リストで shop_search_result を送る（段階表示）
 │     説明文は推薦B の完了後に同じ request_id で更新する
 │
 └─ Live: 確定 5 件、または締め切り（10 秒）の時点で tool_response を 1 回だけ送る
          （読み上げるのは確定した店舗だけ。内容は推薦 LLM 由来の項目のみ）
```

### 5.1 時間の見積もり（未計測の部分は明記）
- **店名だけの出力量**: 1 店舗あたり約 20〜30 トークンになる見込み（現行は約 120）。M1 の生成速度（約 115 トークン/秒）から推定すると、最初のテキスト（p50 1.9 秒）の後、店舗はおよそ 0.2〜0.3 秒間隔で確定する。7 店舗が揃うのは 4 秒前後。**未計測のため M3 で計測する。**
- **初回カード**: 1 店舗目の店名 +（Agent Tools + Details + 判定）。M1 と D1.7E の分布から、p95 でも 5 秒以内に収まる見込み。M3 で確認する。
- **全 5 店舗**: 7 店舗の照合が 4〜6 秒で揃う見込み。曖昧な店舗を選択 LLM（1 店舗あたりの時間は M3 で計測）にかけても、10 秒までに 4 秒程度の余裕が残る見込み。
- **締め切り**: 締め切りまでに確定しない店舗は不採用とする。

### 5.2 品質の扱い
- **推薦内容**: 店名と順位は推薦A だけが決め、推薦B は説明だけを生成する。分割によって推薦内容・順位・推薦理由の質が変わらないことを、33秒版・現行一括推薦との比較で確認する（M3）。
- **同一性**: §3 の軽量判定 + 曖昧なものだけ選択 LLM（オフライン評価で D と同等以上）。
- **実在しない推薦**: 構造上の上限（§4.3）を超えるには、照合に回す店名を増やす必要がある。推薦A で店名を 7 件より多く出す案（例：10 件）は、確定済みの方針（7 件一括）の変更になるため、承認と品質比較が必要（§7）。

### 5.3 比較した他の案

| 案 | 初回 5 秒 | 正しい 5 件を 10 秒 | 品質・方針 | 判断 |
|---|---|---|---|---|
| v0.1 フロー P（resolveNames の HIGH を即採用） | ○ | ✗（M2: 0/30） | 回収 23.5%、建物の誤採用あり | 不採用 |
| 現行の一括推薦 + 店舗単位照合（§4.2） | 約 63% | 約 11%（理論上限 47%） | 品質は良い | 目標に届かない |
| **フロー S（推奨）** | 見込みあり（M3） | 見込みあり（M3） | 推薦の分割に承認が必要 | **第一候補** |
| フロー Q（Maps 検索を先に行い、その中から選ぶ） | 見込みあり | 見込みあり | 推薦の出どころが変わる。方針変更 | 比較候補として保持 |
| E の 1 位即採用 | ○ | 20% | 別店舗が多い | 不採用 |

### 5.4 Live・ショップカード・UIKA との連携
- **ショップカード**: 既存の `shop_search_result`（フロントは受信のたびに全カードを描き直す）に累積リストを送れば、フロントを変えずに段階表示できる。ただし次の 2 点はフロントの改修が必要（別途承認）。
  - 説明文の後からの更新を安全に扱うこと
  - Google Maps の出典（attribution と placeUrl）を表示すること
- **Live**: tool_response は 1 回だけ送る（現行どおり）。分割送信は前提にしない（Live の仕様は未確認）。
- **変更しないもの**: UIKA FULL133、LAM/A2E、double reset、Greeting。

## 6. 次の統合 PoC（M3）で検証する内容と評価方法

計測専用のコードで行い、製品コードは変更しない。条件は通常の 10 クエリ × 3 回。

| ID | 検証内容 | 方法 | 判定 |
|---|---|---|---|
| M3-1 | 店名先行の推薦A のストリーミング到達時刻 | 7 件（および承認があれば 10 件）の early 確定時刻 | 1 件目 p95 ≤ 3 秒、7 件目 p95 ≤ 5 秒 |
| M3-2 | 推薦A + 推薦B の推薦品質 | 現行一括推薦（33秒版と同じ推薦 LLM）と同じクエリで比較。店名の一致率、順位の変化、説明文の質。人による評価を含む | 33秒版以上 |
| M3-3 | 店舗単位パイプラインの実時間 | 1 店舗ごとの Agent Tools・Details・判定・選択 LLM の時間（バッチではなく 1 店舗単位） | 初回カード p95 ≤ 5 秒、全 5 店舗 p95 ≤ 10 秒 |
| M3-4 | 軽量判定の汎化精度 | 新しい推薦結果で、上位 5 候補を含めて判定（`types` と座標も使う） | 誤採用 ≤ D（5 件/30 試行）、正しい 5 件 ≥ 14/30 |
| M3-5 | 方式 D との同時比較 | 同じ推薦A の出力・同じ Agent Tools 結果から D と v0.2 を作る | 同上 |

**評価方法**
- 同じ入力（推薦A の出力と Agent Tools の結果）から、A（33秒版の Places 照合）・D・v0.2 を作って比較する（D1.7E と同じ方式）。
- **正誤の判定**: 方式どうしを比べるのではなく、「推薦店と採用された実店舗が同一か」を独立に判定する。
  - 判定は店名・住所・業態・Web による確認で行う。
  - 既存ラベルにない新しい候補は正解と推定せず、「独立確認が必要な件数」として別に数える。
- **時刻**: 推薦開始からの経過時間で、店舗ごとのイベント時刻を記録する。中央値の加算ではなく、試行ごとの実時刻で判定する。
- **件数不足**: 5 件に満たない試行は未達とする。
- **API 呼び出し**: Agent Tools、Details、選択 LLM、推薦A・B の回数と、Gemini のトークン数を記録する。

## 7. 判断していただきたい事項
1. 推薦を「店名リスト（推薦A）」と「説明生成（推薦B）」に分ける（推薦プロンプトとスキーマの変更）。品質の確認は M3-2 で行う。
2. 推薦A で出す店名の数を 7 件より増やす（例：10 件）。実在しない推薦による件数不足への対策。品質と時間を M3 で比較する。
3. カードの段階表示と、説明文を後から更新するフロントの改修。Agent Tools の出典表示も含む。
4. 軽量判定を同一性判定の第一段に採用するかどうか（M3-4 の結果で最終判断）。

## 8. リスク
- 軽量判定の規則は 132 件に合わせて調整したため、新しいデータでは精度が下がる可能性がある（M3-4）。
- 推薦を分割することで、推薦の質（順位や店名の選び方）が変わる可能性がある（M3-2）。
- 実在しない店舗の推薦は、推薦 LLM 自体の課題として残る。
- 1 店舗ずつの Agent Tools や選択 LLM の時間は未計測（M3-3）。
- 段階表示による画面のちらつきや、読み上げ開始の時期など、UX は実機で確認が必要。
