## 1. S10 未達 10 試行の原因分析

→ §1 は `gate_m3_analyze`（API 呼び出しなし。`m3_results.json` と `m3_labels.tsv` のみ使用）の出力で確定する。結果は本書の §1 表に記入する（未記入の間は「集計待ち」）。

### 1.1 原因コードと改善対象工程

| 原因コード | 内容 | 改善対象工程 |
|---|---|---|
| FEWER_CARDS | 10 秒時点でカードが 5 枚未満（内訳は下の NOT_FOUND / MISS / LATE / DUPLICATE） | — |
| WRONG_SAME | 採用カードが別店舗、経路は軽量判定 SAME | 軽量判定・検索範囲 |
| WRONG_LLM | 採用カードが別店舗、経路は選択 LLM | 選択 LLM |
| UNKNOWN | 採用カードが判定不能（正解に含めない） | 評価（判定不能） |
| CLOSED | 採用カードが閉業 | 軽量判定（閉業） |
| MISS_LIGHT | 不採用店舗の検索 1 位が正解（軽量判定が DIFFERENT） | 軽量判定 |
| MISS_LLM | 不採用店舗の検索 1 位が正解（選択 LLM が none／誤った候補） | 選択 LLM |
| NOT_FOUND | 不採用店舗の検索 1 位が別店舗・判定不能・閉業、または候補なし | 推薦A（実在性）・検索 |
| LATE | 正解の店舗が 10 秒より後に確定 | 照合の所要時間 |
| DUPLICATE | 同じ place ID の後順位を除外 | 推薦A（同一店の重複） |
| CAP_PUSHED | 10 秒以内に確定した正解店舗が、上位の X/?/Z に押し出されて 5 枚に入らなかった | 上位カードの誤り |
| 表示差し替え | 確定順に即時表示した場合に、上位の後着で既表示カードが押し出される回数（§1.3） | 段階表示の方式 |

制約: 取りこぼしは「検索 1 位」のラベルでしか判定できない（2 位以下に正解があった場合は数えられない）。

### 1.2 試行別一覧

集計待ち（`~/m3_analysis.txt` の §1・§2）。

### 1.3 段階表示の方式

- **即時表示**: 確定した店舗を順位どおりに差し込む。上位の店舗が後から確定すると、5 枚目が押し出され表示が差し替わる。
- **上位確定後表示（差し替えなし）**: 順位 k のカードは、1〜k 位がすべて判定済みになった時点で表示する。差し替えは起きないが、初回カードが遅くなる場合がある。
- 両方式の初回カード時刻・差し替え回数を `gate_m3_analyze` の §5・§5b で算出し、M4 の表示方式を決める。

## 2. 店舗同一性と推薦品質の分離評価

### 2.1 評価軸

1. **同一性**（M3 で実施済み）: O / X / ? / Z
2. **条件適合**（新規）: 採用カードごとに、クエリが指定した条件だけを評価する

| 条件 | 評価方法 | 判定 |
|---|---|---|
| 料理ジャンル | 店の主業態が指定ジャンルか（例: 焼き鳥、天ぷら、ラーメン、串カツ、イタリアン、ジンギスカン、割烹・和食、カフェ） | 適合 / 不適合 / 不明 |
| 場所 | 指定地域内か（「徒歩 N 分」は距離、地名は行政区・駅圏） | 同上 |
| 予算 | 指定予算帯に入るか | 同上 |
| 同行人数・個室 | 指定人数で個室利用ができるか | 同上 |
| 利用目的 | 接待・記念日・子連れ・落ち着いて過ごす等に合うか | 同上 |

- 「不明」は適合に数えない。
- 根拠は、推薦A・B の LLM 出力と評価者の知識、およびすでに表示済みの店名・住所に限る。Google Maps のコンテンツを評価用 LLM に渡さない。
- 予算と個室は、評価者の知識だけでは「不明」が多くなる見込み。人による確認（公式サイト等）を推奨する。

### 2.2 SAME と判定された別店舗・判定不能の原因特定

- `gate_m3_analyze` の §4 で、SAME 経路の X / ? 全件について、軽量判定の理由と検索範囲（地名・半径・半径の根拠）を列挙する。
- M3 集計時点で判明している別店舗は「串かつ まる」の 1 件（S7・S10 で各 1 回）。梅田のクエリで、検索範囲の地名が「大阪」に解決され、半径 10km になっていた。

### 2.3 判定ルールの検証データ分離（必須）

- M3 の 30 試行（306 ペア）は**開発データ**とする。これを見て軽量判定・検索範囲・選択 LLM の規則を変えた場合、同じデータで新方式の精度は報告しない。
- 規則を修正するときは、修正前に**規則の版（commit SHA）を固定**してから、未使用データで評価する。
- 未使用データ: M4 では、M3 と重複しない新しいクエリを使う。地域・ジャンルを変え、徒歩条件・駅名・ホテル内・商業ビル内を含める。
- 新データの正誤ラベルは、方式の判定結果（経路・理由）を見ずに付ける。判定不能は正解に含めない。

## 3. 推薦B（説明文）の遅延解消

### 3.1 M3 で判明している事実

| 項目 | S10 の値 |
|---|---|
| 推薦A 1 店舗目の店名 | p50 2.53s |
| 推薦A 10 店舗目の店名 | p50 5.14s、p95 6.19s |
| 正しい 5 店舗の確定 | p50 6.29s、p95 8.67s、最大 9.55s |
| 推薦B 完了 | p50 17.07s（10 秒以内 0/30） |
| 選択 LLM（1 店舗） | p50 2.9s、p95 3.6s |

- 推薦B は推薦A の完了後に始まり、全候補（S10 は 10 店舗）の説明をストリーミングなしで一括生成する。
- 出力トークンは S7・S10 の 60 回の合計で 54,156 だった。
- B 単体の所要時間は約 12 秒と推定する。中央値どうしの差（17.1s − A 完了 約 5.1s）から出した概算で、計測値ではない。
- tool_response は現行どおり 1 回だけ送る。分割送信には依存しない。そのため、Live の読み上げ内容は**送信時点で 5 店舗分すべて揃っている必要がある**。

### 3.2 方式の比較

| 項目 | 方式 A: 確定 5 店舗の説明を一括生成 | 方式 B: 店舗ごとに短い説明を並列生成 | 方式 C: Live には店名＋短い説明、詳細は後からカード更新 |
|---|---|---|---|
| 開始時点 | 5 店舗確定（p50 6.3s、p95 8.7s） | 各店舗の店名を受信した時点（照合と並行） | 短い説明: B と同じ。詳細: 推薦A 完了時に全候補を順位順にストリーミング |
| 生成量 | 5 店舗 × 詳細 | 1 店舗 × 短文（1〜2 文）× 最大 10 回 | 短文 × 最大 10 ＋ 詳細 × 10（ストリーミング） |
| tool_response の送信 | B 完了後。概算 12〜15 秒（未計測） | 5 店舗確定＋その店舗の短文が完成した時点。概算 7〜9 秒（未計測） | 方式 B と同じ |
| Live の読み上げ内容 | 詳細（現行と同じ質） | 短文のみ | 短文のみ |
| カードの説明 | 詳細（遅い） | 短文のみ | 短文を先に出し、詳細で更新 |
| 推薦理由の質 | 現行と同等（店舗間の比較を含む） | 低下の恐れ（店舗ごとの単独生成で、他店との違いを書けない） | カードは現行と同等。Live は短文 |
| LLM 呼び出し | +1 | +10（レート制限の確認が必要） | +10 ＋ 1 |
| 主なリスク | 説明が 10 秒に間に合わない | 文の質・重複・事実の創作 | 短文と詳細の矛盾、カード更新時のちらつき |

### 3.3 推奨: 方式 C（短い説明は方式 B の並列生成、詳細はストリーミング一括生成）

1. 推薦A の店名を受信するたびに、照合と並行して「短い説明」生成を開始する。
   - 入力: ユーザーの依頼、店名、地区。Maps の情報は渡さない。
   - 不採用になった店舗の結果は捨てる。
2. 5 店舗確定（または 10 秒締め切り）の時点で、確定した店舗の短い説明が揃い次第 tool_response を 1 回送る。中身は店名・地区・ジャンル・短い説明で、すべて LLM 由来。
3. 推薦A の完了時に、詳細説明の一括生成を `stream=true` で開始する（全候補、順位順）。項目が 1 件確定するたびに、採用済みカードの説明を更新する。
4. 品質の担保: 短文と詳細を同じ request_id・順位で突き合わせる。矛盾（ジャンル・価格・特徴）が無いことを M4 で評価する。

方式 C を選ぶ理由:
- tool_response の 1 回送信を維持したまま、送信を「5 店舗確定」の直後まで早められる見込みがある。
- カードの推薦理由は、現行と同じ一括生成（店舗間の比較あり）を維持できる。

方式 C で確認が必要な点（M4 で計測。未計測のまま採用しない）:
- 短い説明 1 件の所要時間と、10 並列時のレート制限・エラー率。
- 短い説明を待つことで、tool_response の送信が 5 店舗確定からどれだけ遅れるか。
- 短文の質（指定条件への適合、事実の創作、他店との重複表現）と、詳細との矛盾率。
- 詳細ストリーミングの各店舗の完了時刻（上位 5 店舗の説明がカードに反映される時刻）。

### 3.4 Live に渡す内容の制約

- tool_response には LLM 由来の項目だけを入れる（現行 `build_narration_item` と同じ）。Google Maps のコンテンツ（summary、Details の評価・住所など）は入れない。
- Agent Tools の summary は、選択 LLM のグラウンディングにだけ使う。

## 4. M4 統合計測の設計

### 4.1 計測する工程と時刻の定義

基準時刻 T0 は、バックエンドが `search_shops` の tool_call を受信した時刻（単調時計）とする。

| # | 事象 | 計測側 | 既存ログ／追加 |
|---|---|---|---|
| E0 | ユーザー発話の最終文字起こし受信（参考） | ブラウザ（`user_transcript` 受信） | 追加（console.log のみ） |
| E1 | search_shops tool_call 受信（T0） | バックエンド | 追加（ログのみ） |
| E2 | `shop_search_start` 受信（ブラウザ T0'） | ブラウザ | 追加（console.log のみ） |
| E3 | 推薦A の最初のテキスト、各店舗の店名確定 | バックエンド | 新エンジン内 |
| E4 | 各店舗の Agent Tools・Details・軽量判定・選択 LLM の完了 | バックエンド | 新エンジン内 |
| E5 | カード送信（k 枚目） | バックエンド | 新エンジン内 |
| E6 | カード受信・描画完了（k 枚目。DOM 挿入後の requestAnimationFrame） | ブラウザ | 追加（console.log のみ） |
| E7 | 短い説明の完成（店舗ごと） | バックエンド | 新エンジン内 |
| E8 | 正しい 5 店舗の確定（t_set） | バックエンド | 新エンジン内 |
| E9 | tool_response 送信 | バックエンド | 既存ログ `function_response_sent ... t=` |
| E10 | tool_response 後、最初の `live_audio` 受信 | ブラウザ | 既存ログ `[TRACE AUDIO] perf=` |
| E11 | 音声の再生開始（再生位置が進み始めた時刻） | ブラウザ | 既存ログ `[TRACE AUDIO] playback=` |
| E12 | tool_response 後、最初の `live_expression` 受信（UIKA FULL133 への既存連携が動いていることの確認） | ブラウザ | 既存ログ `[TRACE EXPR]` |
| E13 | 詳細説明のカード反映（店舗ごと） | バックエンド送信・ブラウザ描画 | 新エンジン内＋追加 |
| E14 | 読み上げターン完了 | バックエンド | 既存ログ `[ShopDesc] LiveAPI読み上げ完了` |

### 4.2 指標（バックエンド内部時刻とブラウザ表示時刻を分ける）

| 指標 | バックエンド内部（E1 基準） | ブラウザ表示（E2 基準） | 目標 |
|---|---|---|---|
| 初回カード | E5(1) − E1 | E6(1) − E2 | 5 秒 |
| 正しい 5 店舗 | E8 − E1（正誤は独立ラベル） | E6(5) − E2 | 10 秒 |
| tool_response | E9 − E1 | — | 計測のみ |
| Live 音声開始 | — | E10 − E2、E11 − E2 | 別指標（目標は M4 結果で決める） |
| 詳細説明の反映 | E13 − E1 | E13(描画) − E2 | 計測のみ |
| 発話終了から検索開始（参考） | — | E2 − E0 | 計測のみ（Live 側の判断時間。改善対象外） |

時計の扱い:
- バックエンドとブラウザの時計は直接比べない。
- ブラウザ側の値は、`shop_search_start` を受信した時刻からの経過として計測する。この方法では、`shop_search_start` が届くまでの片道遅延が含まれない。そのため、Socket.IO の往復時間を試行ごとに 1 回測り、その半分を補正の参考値として併記する。
- カード等の各イベントの payload に、request_id とバックエンド側の経過 ms（E1 基準）を入れる。ブラウザはそれを受信時刻と並べてログに出す。

### 4.3 計測方法

- **環境**: 本番とは別のプレビュー環境（PR #137 のプレビュー）。本番リビジョン・トラフィック・環境変数は変更しない。
- **入力**: Live に音声または文字で依頼する。人の発話は再現性が低いため、毎回同じ依頼文を読み上げる。
- **クエリ**: §2.3 の未使用データ（新しい 10 クエリ）× 3 回。
- **比較対象**: S10 のみ（D・S7 は計測しない）。
- **ログの回収**: バックエンドは Cloud Logging の `[NewShopRec]` 行、ブラウザは DevTools コンソールの保存（`[M4]`・`[TRACE AUDIO]`・`[TRACE EXPR]`）。
- **品質評価**:
  - 同一性: O/X/?/Z を独立判定し、方式の経路は見ずに付ける。
  - 条件適合: §2.1 の基準。
  - 短い説明と詳細説明: 矛盾の有無、事実の創作、条件への適合。
- **合否条件**（M4）:
  - ブラウザ表示で初回カード ≤5 秒が 30/30。
  - 正しい 5 店舗 ≤10 秒が M3 の S10（20/30）以上。
  - 誤採用 ≤ D の 5/30。
  - 既存音声連携の確認として、UIKA FULL133 で tool_response 後の `live_expression` が通常どおり届き、読み上げが最後まで完了する。

### 4.4 計測用の追加（実装時の変更点。いずれも承認が必要）

| ファイル | 変更 | 既存動作への影響 |
|---|---|---|
| `new_shop_recommendation/`（新エンジン） | S10 フロー（推薦A ストリーミング、店舗単位照合、短い説明、詳細ストリーミング）と、各事象の時刻ログ | 新エンジン内のみ |

## 5. Google Maps の出典表示（統合仕様）

- **カード**: Agent Tools で照合した店舗のカードには、Agent Tools の `attribution`（title・url）と `googleMapsLinks.placeUrl` を保持し、表示する。
  - 新エンジンは `maps_attribution` と `maps_url` をすでにカードに入れている（`agent_tools_places.py` の `details_for_card`）。
  - フロント（`ShopCardList.astro`）は現在 `maps_attribution` を表示していない。M4 で表示を追加する。
- **summary**: Agent Tools の summary は、選択 LLM のグラウンディングにだけ使う。画面・Live の読み上げ・ログ・保存には出さない。summary から店名等をプログラムで抜き出さない。
- **Place Details の内容**: カードの表示（店名・評価・住所・地図リンク）に使う。Live の読み上げ（tool_response）には入れない。保存しない。
- **計測ログ**: place ID と時刻だけを残す。店名・住所・座標は残さない（M3 の `strip_for_save` と同じ方針）。
- 根拠は v0.2 設計書 §3.5 と同じ（Maps Grounding Lite / Agent Tools の Service Specific Terms §10.2.1・§10.3.1）。表示の文言・形式は実装前に規約本文で再確認する。
