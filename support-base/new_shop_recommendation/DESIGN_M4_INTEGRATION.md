## 0. 結論

1. S10 の正しい 5 件（10 秒以内）20/30 のうち、**既存データで回復を確認できるのは最大 2 試行（3・30）**。条件は、選択 LLM の誤採用を不採用にできること。
   - 判定不能 5 試行は、人による証拠確認が済むまで正解にしない。
   - 店舗不足 3 試行は、既存データでは回復できない（§1）。
2. **表示方式**: 初回カード 5 秒を満たすには、上位確定後表示（順位保証）だけでは足りない。試行 1〜19 のうち 3 試行で 1 位の判定に 6.4〜7.3 秒かかっている。暫定表示と追記のみ表示の比較値は `gate_m3_m4` で確定する（§2）。
3. **説明文**: 推奨は**方式 C**。tool_response は 5 店舗確定の時点で、確認済みの店名と LLM 由来の簡潔な情報だけを 1 回送る。詳しい推薦理由は、後からカードに追加する。説明文を待つためにカードや Live を遅らせない（§3）。
4. **品質の必須条件**: 元の 33 秒版以上の推薦品質。33 秒版は M3 で計測できていない（推薦用キーで 404）。そのため、**M4 で同じ新クエリに対して 33 秒版の基準を取ることを、合格判定の前提にする**（§6）。

## 2. 表示方式

### 2.1 評価の修正

旧 `replacement_events()` は、5 枚上限で新しい店舗を表示しなかっただけの事象も差し替えと数えていた。次のように分けて数える。

- **真の差し替え**: 表示中のカードが表示から外れる。
- **5 枚上限による非表示**: 新しく確定した店舗が上位 5 件に入らず、表示されない。
- **位置ずれ**: 上位の店舗が後から確定し、既存カードの位置が下がる（表示から外れない）。
- **同一 place の別表記**: 表示は変えない。

### 2.2 比較する 3 方式（同じ 30 試行・10 秒）

| 方式 | 内容 | 長所 | 短所 |
|---|---|---|---|
| 暫定表示 | 判定済みの採用店舗のうち、推薦順位の上位 5 件を常に表示する | 初回が最速。最終 5 件は推薦順位どおり | 差し替えが起きる |
| 上位確定後表示 | 順位 k のカードは、1〜k 位がすべて判定済みになってから表示する | 差し替えなし、順位保証 | 1 位が選択 LLM 経路だと初回が遅れる。試行 6・15・16 は初回 6.4〜7.3 秒 |
| 追記のみ | 判定順に最大 5 件を出し、出したカードは消さない | 差し替えなし、初回が最速 | 最終 5 件が推薦順位の上位 5 件と異なる場合がある |

数値（初回 ≤5 秒、初回が正しい店舗か、5 枚目の時刻、最終 5 枚の正誤、差し替え回数）は `gate_m3_m4` §5 で確定する。

**採用基準**（数値確定後に適用）:
1. 初回カード ≤5 秒が 30/30 でない方式は採らない。上位確定後表示は、この時点で除外される見込み。
2. 暫定表示と追記のみのうち、「最終 5 枚が全て O」が多い方を採る。
3. 同数なら、差し替え 0 の追記のみを採る。

推薦B の品質で判明していること（事実）:
- 同じ店（美鶏）について、試行間で食材が矛盾している（高坂鶏／信玄どり）。
- 根拠のない受賞歴（「ミシュラン掲載」）を書いた例がある。
- 条件に合わないことを説明文自身が認めている例がある（知留久「着席スタイル」、鳥よし「やや高価格帯」）。

### 3.2 方式比較

| 観点 | A: 確定 5 店舗をまとめて生成 | B: 確認できた店舗から短い説明を並列生成 | C: 店名と確認済みの簡潔な情報で応答し、詳細は後からカードへ |
|---|---|---|---|
| tool_response の時刻 | 5 店舗確定 ＋ 5 店舗分の生成。約 12〜15s（概算、未実測） | 5 店舗確定 ＋ 最後の店舗の短文生成の残り。短文 1 件は参考値で約 3s。照合と並行すれば待ちは 0〜3s（未実測） | **5 店舗確定の時点**（説明生成を待たない。追加待ち 0） |
| 推薦内容の品質 | 現行と同じ（店舗間の比較あり） | 店舗ごとの単独生成で、比較の観点が落ちる恐れ | カード: 現行と同じ詳細（後から追加）。Live: 確認済み情報のみ |
| Live 読み上げの自然さ | 詳細を読む。長い | 短文を読む。自然 | 店名・地区・ジャンル・推薦の要点（推薦A の出力）だけで、内容は少ない。「詳しくはカードで」と案内する |
| API コスト（1 回の検索あたり） | ＋1 回（入力 5 店舗分） | ＋最大 10 回（並列。レート制限の確認が必要） | 詳細生成 ＋1 回（現行と同じ） |
| 10 秒目標との両立 | ✗ | 未検証 | ○（tool_response は 5 店舗確定に連動。p95 8.67s は実測） |
| 事実創作のリスク | 現行と同じ | 短文でも同じリスク | Live 側は最小。カード側は現行と同じ |

### 3.3 推奨: 方式 C

1. **tool_response**（1 回だけ）: 5 店舗確定の時点で、または 10 秒の締め切りで、確定した店舗を順位順に送る。
   - 各店: 店名（推薦A）、地区（推薦A の area_hint）、ジャンル（依頼の料理ジャンル）。
   - Google Maps の情報（住所・評価・summary 等）は入れない。
   - Live への指示: 「各店の詳しい特徴と推薦理由は画面のカードに表示しています。渡した項目以外の特徴・価格・受賞歴を述べないでください」。
2. **詳細な推薦理由**: 推薦A の完了時（p50 5.1s）に、全候補の詳細生成を `stream=true` で順位順に開始する。項目が 1 件完成するたびに、採用済みカードの説明を更新する。
   - 不採用の店舗の説明は捨てる。
   - 店名・順位の変更は検証で拒否する（M3 の `validate_b` と同じ）。
3. **方式 B は送らずに計測だけする（M4）**: 短い説明を並列生成するが、Live にもカードにも使わない。完成時刻・失敗率・品質だけを記録し、方式 C の Live 内容を補強する価値があるかを判断する。
4. 説明文を待つためにカード配信や tool_response を遅らせる設計は採らない。

### 3.4 Live 読み上げの確認事項（M4 で計測）

- 渡した項目以外の事実（価格・受賞歴など）を Live が話さないか。読み上げ文字起こし（既存 `ai_transcript`）で確認する。
- 読み上げ開始時刻（§4.2）。
- 読み上げが最後まで完了するか（既存ログ `[ShopDesc] LiveAPI読み上げ完了`）。

## 4. M4 全体フロー

```
[ブラウザ] 発話 ─▶ [Gemini 3.8 Live] search_shops tool_call
                                   │ E1（バックエンド T0）
                                   ▼
[バックエンド] shop_search_start を送信 ──────────────▶ [ブラウザ] 待機表示（E2 = ブラウザ T0'）
   │
   ├─ 推薦A（gemini-3.8-flash LOW、stream、tools なし）: rank・店名・地区を 10 件
   │     店名が 1 件確定するたびに ─▶ 店舗ごとの照合（並列）
   │        Agent Tools searchText → Place Details → 軽量判定
   │        SAME: 確定 / AMBIGUOUS: 選択 LLM（summary はここでだけ使う） / DIFFERENT: 不採用
   │        → 店舗確定（E4）→ 表示方式（§2）に従いカード送信（E5）─▶ [ブラウザ] 描画（E6）

                                  └▶ A2E live_expression ─▶ UIKA FULL133（既存のまま。E12）
```

| E14 | 読み上げ完了 | バックエンド | 既存 `[ShopDesc] LiveAPI読み上げ完了` |

### 4.2 指標（区別して報告する）

| 指標 | 定義 |
|---|---|
| バックエンドのカード確定時間 | E4／E5 − E1（初回と 5 枚目） |
| ブラウザ表示時間 | E6 − E2（初回と 5 枚目） |
| 5 店舗の最終確定時間 | E8 − E1。正誤は独立ラベル |
| Live 読み上げ開始時間 | E10 − E2（受信）、E11 − E2（再生開始） |
| 参考: 発話終了から検索開始まで | E2 − E0（Live の判断時間。改善対象外） |

- バックエンドとブラウザの時計は直接比べない。ブラウザ側の値は `shop_search_start` を受信した時刻からの経過で測る。
- 各イベントの payload に request_id とバックエンド経過 ms を入れる。
- 片道遅延は含まれないため、Socket.IO の往復時間の半分を補正の参考値として併記する。

### 4.3 Google Maps の出典表示

- **カード**: Agent Tools の `attribution`（title・url）と `googleMapsLinks.placeUrl` を表示する。
  - 新エンジンは `maps_attribution` と `maps_url` をすでにカードに入れている（`agent_tools_places.py` の `details_for_card`）。
  - フロント（`ShopCardList.astro`）は現在 `maps_attribution` を表示していない。M4 の実装で追加する。
- **summary**: 選択 LLM のグラウンディングにだけ使う。画面・Live・ログ・保存には出さない。プログラムで店名等を抜き出さない。
- **Place Details の内容**: カードの表示にだけ使う。tool_response（Live）には入れない。保存しない。
- **計測ログ**: place ID と時刻だけを残す。
- 表示の文言・形式は、実装前に Service Specific Terms の本文で再確認する。

## 6. 推薦品質の評価（33 秒版以上が必須条件）

評価する軸（店舗同一性とは別に評価する）:

| 軸 | 判定 |
|---|---|
| 店舗同一性 | O / X / ? / Z（既存） |
| 料理ジャンル | 適合 / 不適合 / 不明 |
| 地域 | 指定地域・徒歩範囲内か |
| 予算 | 指定予算帯に入るか |
| 人数・個室 | 指定人数・個室条件に合うか |
| 利用目的 | 接待・記念日・子連れ・立ち飲み・落ち着いて過ごす 等 |
| 説明文の事実性 | 創作（受賞歴・価格・食材の矛盾）の有無 |

- 「不明」は適合に数えない。予算・個室は、人による確認（公式サイト等）を含める。
- 評価者には、どの方式の出力かを伏せる。
- **33 秒版との比較**: 同じ未使用クエリで、33 秒版（本番 8d30e55 と同じプロンプト・モデル・検索）を実行し、同じ軸で評価する。
  - 33 秒版の実行には、本番リビジョンの `GEMINI_API_KEY` を計測スクリプト内で読む必要がある（M3 では推薦用キーで 404）。**承認が必要**。
- M3 で確認できた推薦品質の問題（S10、試行 1〜19 と確認リスト）:
  - 立ち飲みの条件に着席型の店が混ざる（試行 10 で 5 店中 3 店）。
  - 予算超過を説明文自身が認めている（鳥よし）。
  - 地域外の店（銀座の依頼に日本橋の「天ぷら 浅沼」、新宿の依頼に南青山の「外苑前 僖成」が採用候補）。
  - ホテル名の推薦（HOTEL EMANON）。
  - 割烹の依頼に鮨店（鮨まつもと）。
